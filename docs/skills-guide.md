# Памятка по Agent Skills

## 1. Пример расположения skills в проекте

```text
my-project/
├── AGENTS.md
├── package.json
├── src/
├── tests/
└── .agents/
    └── skills/
        ├── implementing-react-feature/
        │   ├── SKILL.md
        │   ├── scripts/
        │   │   ├── verify-change.sh
        │   │   └── collect-changed-files.py
        │   ├── references/
        │   │   ├── architecture.md
        │   │   ├── component-patterns.md
        │   │   └── testing-strategy.md
        │   ├── assets/
        │   │   ├── component-template.tsx
        │   │   └── report-template.md
        │   └── agents/
        │       └── openai.yaml
        │
        ├── reviewing-typescript/
        │   ├── SKILL.md
        │   └── references/
        │       └── review-checklist.md
        │
        └── debugging-build/
            ├── SKILL.md
            ├── scripts/
            │   └── collect-diagnostics.sh
            └── references/
                └── common-errors.md
```

### Назначение файлов и директорий

`SKILL.md` - Главная инструкция
Содержит метаданные, условия активации и основной рабочий процесс агента

`scripts/` - Готовые скрипты для сценариев
Для повторяемых действий типа деплоя или чего-то постоянного

`references/` - Справочные материалы
Пример: архитектура, правила, API, чек-листы и подробности, которые читаются только при необходимости - хранит большие доки.

`assets/` - Шаблоны и ресурсы
Хранит для примера заготовки кода, шаблоны отчётов, схемы, конфигурации и другие файлы для результата.

`agents/openai.yaml` - Настройки Codex
Опционально задаёт отображение skill, зависимости и дополнительные параметры для Codex.

`AGENTS.md` - Общие правила проекта
Содержит инструкции, которые должны применяться почти к любой задаче в репозитории.

# 3. YAML-метаданные

`name: implementing-react-feature`
Имя — идентификатор
Уникальное имя skill в нижнем регистре с дефисами.

`description: Implements React features...`
Описание — активация
Объясняет, что делает skill, когда его применять и по каким словам агент должен его выбрать.

`license: MIT`
Лицензия — условия использования
Указывает лицензию skill или путь к файлу с полными условиями.

`compatibility: Requires Node.js...`
Совместимость — требования среды
Перечисляет необходимые программы, платформы, доступ к сети или особенности окружения.

```yaml
metadata:
  author: project-team
  version: "1.0"
```

Метаданные — служебные сведения
Хранят автора, версию и другие дополнительные строковые свойства.

`allowed-tools: Bash(git:*) Read Grep`
Разрешённые инструменты
Предварительно разрешает отдельные инструменты и команды, если агент поддерживает это поле.

# 4. Рекомендуемые разделы SKILL.md

`# Implementing React Features`
Название — назначение skill
Кратко называет рабочий процесс или способность, которую получает агент.

`## Purpose`
Цель — ожидаемый результат
Объясняет, какую проблему решает skill и какой результат должен получить пользователь.

`## When to use`
Условия — когда применять
Перечисляет задачи, запросы и ситуации, при которых skill должен активироваться.

`## Do not use`
Границы — когда не применять
Показывает похожие задачи, для которых нужен другой skill или обычный режим агента.

`## Required context`
Контекст — что изучить
Перечисляет файлы, документацию и состояние проекта, которые нужно проверить до изменений.

`## Inputs`
Входные данные — что требуется
Описывает аргументы, файлы, ссылки, ветки или сведения, необходимые для выполнения задачи.

`## Workflow`
Процесс — порядок действий
Задаёт пошаговый алгоритм от исследования задачи до реализации и проверки результата.

`## Project conventions`
Соглашения — правила проекта
Указывает локальные архитектурные паттерны, стиль именования и предпочтительные инструменты.

`## References`
Справочники — что читать
Объясняет, какой файл из `references/` нужно открыть в конкретной ситуации.

`## Scripts`
Скрипты — что запускать
Описывает назначение команд из `scripts/`, аргументы запуска и ожидаемый результат.

`## Assets`
Ресурсы — что использовать
Указывает, какие шаблоны и заготовки из `assets/` использовать при генерации результата.

`## Guardrails`
Ограничения — чего не делать
Перечисляет опасные, нежелательные или запрещённые действия.

`## Error handling`
Ошибки — как восстанавливаться
Объясняет действия при падении команды, отсутствии зависимости или неполных входных данных.

`## Edge cases`
Особые случаи — исключения
Описывает редкие ситуации, в которых основной процесс необходимо изменить.

`## Verification`
Проверка — как валидировать
Перечисляет тесты, линтеры, сборку, typecheck и другие проверки результата.

`## Completion criteria`
Готовность — Definition of Done
Определяет условия, без выполнения которых агент не должен считать задачу завершённой.

`## Output format`
Формат — как отвечать
Задаёт структуру итогового отчёта, созданного файла, комментария или code review.

`## Examples`
Примеры — вход и результат
Показывает несколько характерных запросов и ожидаемое поведение агента.

`## Common mistakes`
Ошибки — типичные промахи
Перечисляет распространённые неправильные решения и способы их избежать.

# 5. Что куда помещать

Постоянное правило для всех задач
`AGENTS.md`
Например: стиль TypeScript, структура проекта, запрещённые зависимости.

Пошаговый процесс конкретного типа работы
`SKILL.md`
Например: реализация React-фичи, расследование бага или проведение code review.

Большая документация
`references/*.md`
Например: описание архитектуры, API или правила тестирования.

Повторяемая команда
`scripts/*`
Например: сбор диагностики, валидация миграции или запуск набора проверок.

Шаблон результата
`assets/*`
Например: шаблон компонента, конфигурация или структура отчёта.

# 6. Практические правила

1. Один skill должен описывать один связный рабочий процесс.

2. В `description` нужно указывать не только назначение, но и условия активации.

3. Основной `SKILL.md` следует держать коротким, а подробности выносить в `references/`.

4. Не писать общие советы вроде «создавай качественный код», если агент и так это знает.

5. Давать точные команды только там, где важна повторяемость и безопасность.

6. Для каждого reference-файла указывать, когда именно его нужно читать.

7. Для каждого скрипта описывать входные параметры, ожидаемый вывод и обработку ошибок.

8. Завершать skill явными критериями готовности и проверками.

9. Сначала тестировать skill на нескольких реальных задачах, затем дополнять его инструкциями.

10. Не копировать чужой skill без проверки его скриптов, разрешений и зависимостей.
